calm dog down

2026-08-08

A fun, useful app built with Cline+Gemma4:31b for your dog.

Agent Setup

  • Cline + openai-compact:gemma4:31b housed on our server (VS Code plugin)
  • I added a .clinerules directory at the top to specify what a commit message should look like and overall developer styling (casing, organization, etc.)
  • Then I added a memory-bank by asking Cline to "Initialize a memory bank" — this looks at the directory and generates a few files. These were overly wordy and duplicative, so I asked it to consolidate them down to three (one for stakeholders/overview, one for tech, and one for developers — architecture diagrams in Mermaid, testing, etc.)
  • Then I fired away commands with subagents, native tool calling, autocompact, checkpoints, and hooks enabled, with a 256k token maximum for context.

What Failed

  • Perhaps due to the model version or server setup, but I encountered many 400 errors and failed tool calls (especially as the context neared 256k).
  • It seemed to ignore many .clinerules — e.g., not following test-driven development (unless I explicitly prompted it), not updating the memory bank/docs, etc.
  • It waits indefinitely without timeouts for scripts (e.g., ./test.sh when the code has an infinite loop) — Cline then claims "it's thinking..." and never finishes.
  • When it stalled, I sometimes had to close VS Code and then resume — but resume didn't work, or /newtask was disabled, or the button to execute was greyed out.

What Worked

  • For the timeout errors, I simply exited the script (Ctrl+C) and sometimes had to close VS Code and resume the task.
  • Test-driven development: prompt it with a workflow in mind (e.g., a report sent via SMTP) and make sure it adds a test; I find it does a great job with the right feedback/test suite.
  • Then, make sure it doesn't delete tests unless prompted; just like regular development, this helps prevent regression, and Cline works really well with binary feedback from testing.
  • Keep it simple and stupid / self-contained; it's like a junior developer with limited context, but you can ping it a zillion times without overworking them :)
  • Make sure versions are pinned; even if it's a simple Python app, pin versions (or ask it to); its rate of hallucination drops significantly, and your project is more likely to not become shelfware.
  • Make sure you set line limits or ensure code organization is sound; if you have a massive HTML file that grows, it will not fit in context, and grepping line by line will kill you (or your agent, to be specific).

Cline Next Steps

  • Hooking this up with git worktrees (e.g., commits are tasks now).
  • Adding a CI/CD pipeline to ground the agent.
  • Rethinking meta-level invariants / .clinerules — I don't think text is enough for it to execute properly.
  • Voice cloning with a free provider?

App Features

  • This app will be great — it calls Google TTS for voice samples, Groq for sample phrases for Cooper, and then uses an MAB/epsilon-greedy policy to discern the phrase and pitch to fire off should a bark/sound above a certain frequency arise.
  • I LOVE that caching works now, so every run is not a pain to set up, and that reporting works and sends me something interesting via email so I know if my dog is annoying my neighbors.
  • I'm upset about ElevenLabs and their predatory API pricing... capitalists ruining everything (oh wait, I'm American too...)

App Next Steps

  • Dynamically add phrases; e.g., experiment with the length of phrases (words), cadence/pitch throughout the response, and have a causal or correlation dashboard in the reports.
  • Save off MP3s of XX seconds after each phrase fires to the email account (housed in Drive, for instance); up to some XX in megabytes or something.
  • Some ability to discern a dog bark from a human walking by or a siren would be nice to prevent confusion.
  • Continuing to use this and seeing if it's helpful or not (e.g., we need some more causal reasoning in the reports or proven measures of effectiveness).
  • Using OpenRouter instead of Groq because of vendor lock-in (as SPCX aims to establish a profitable service...)
  • Explore a non-browser-based variation (e.g., just a shell script or executable) that I could distribute.
  • See if the software could be housed on a Raspberry Pi or some other smaller controller to remove the requirement that a user keep their laptop running in the background...
